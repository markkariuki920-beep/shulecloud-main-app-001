# ShuleCloud — Cloudflare Pages deployment

ShuleCloud uses TanStack Start with Nitro. It is a full-stack application: the browser bundle is served as static assets while API routes and server functions run in the Cloudflare Pages Worker generated by Nitro. **Do not deploy this project as a static-only Vite site.** Hosting is deliberately selectable: the default Nitro target is a standard Node server, while Cloudflare Pages is an explicit deployment target.

## Build configuration

The repository selects the `cloudflare_pages` preset for this deployment through `npm run build:cloudflare`; the default `npm run build` is not tied to Cloudflare. Nitro's Pages preset writes the deployable output to `dist/`, including the `_worker.js` advanced-mode entry and generated `_routes.json`.

In Cloudflare Dashboard → Workers & Pages → your Pages project → Settings → Builds & deployments, use:

- Framework preset: **None** (or leave framework detection unchanged if it already builds correctly)
- Build command: `npm run build:cloudflare`
- Build output directory: `dist`
- Root directory: the repository root (the folder containing `package.json`)
- Production and Preview: configure the required variables/secrets separately in each environment.

Do not set the output directory to `dist/client`, `.output/public`, or `build`; the Nitro Cloudflare Pages preset's output directory is `dist`.

## Cloudflare runtime compatibility

The Nitro Pages preset generates the Worker and Pages routing files and enables the required Node compatibility support. `npm run build:node` instead produces a standard Node server build for compatible Node hosts. Keep the compatibility date in `nitro.config.ts` current only when you are ready to test the application against the newer Cloudflare runtime.

## Environment variables

Add these under the Pages project's Settings → Variables and Secrets. Use the same variable names in Production and Preview where each environment needs them. Never commit actual credentials to this repository.

### Browser-visible values (not secrets)

- `VITE_SUPABASE_URL` — existing backend's browser-accessible URL.
- `VITE_SUPABASE_PUBLISHABLE_KEY` — existing backend's publishable key.
- `VITE_CLOUD_API_URL` and `VITE_CLOUD_PUBLIC_KEY` — optional aliases used by the provider configuration helper, not substitutes for the generated browser client's required variables.

These are embedded in browser assets by design. Supabase Row Level Security (RLS) must protect every exposed table. Never put a service-role/secret key in either variable.

### Authentication redirect allowlist

In Supabase Dashboard → Authentication → URL Configuration, set the Site URL to `https://shulecloud.pages.dev` (or your own live ShuleCloud domain) and add `https://shulecloud.pages.dev/auth` and `https://shulecloud.pages.dev/reset-password` to the Redirect URLs allowlist. Add Preview URLs only if you use them. Signup and password reset request the current ShuleCloud origin. In Authentication → Email Templates, use Supabase’s `{{ .ConfirmationURL }}` action link; never hardcode a former editor/project URL. If a confirmation message still opens an old URL, correct the Site URL/template and send a new email because already-sent links may retain the old redirect.

### Server-side variables

- `CLOUD_PROVIDER` = `supabase`
- `CLOUD_API_URL` — Supabase project URL (server-side alias).
- `CLOUD_PUBLIC_KEY` — Supabase publishable key (server-side alias).
- `SUPER_ADMIN_EMAIL` — configured Super Admin account email; keep it server-side/private (mark as Secret in Cloudflare). This setting alone does not authenticate an account.
- `APP_URL` — exact public HTTPS origin of this ShuleCloud deployment.
- `GOOGLE_DRIVE_CLIENT_ID` — OAuth client ID.
- `EMAIL_FROM` — sender identity on a verified email domain.

### Server-side secrets (mark as Secret in Cloudflare)

- `CLOUD_SERVICE_KEY` — Supabase service-role/secret key.
- `INTEGRATIONS_ENCRYPTION_KEY` — strong random encryption key used for stored integration credentials. Keep it stable; rotating it without a planned data re-encryption process can make previously stored credentials unreadable.
- `SHULECLOUD_CRON_SECRET` — long random secret used to authorize the scheduled endpoint.
- `SHULECLOUD_CRON_SECRET_PREVIOUS` — optional previous secret during a controlled rotation; remove it after all schedulers use the new secret.
- `GOOGLE_DRIVE_CLIENT_SECRET` — private OAuth client secret.
- `RESEND_API_KEY` — private email-provider API key.

The generated clients and authentication middleware require `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and, for privileged server operations, `SUPABASE_SERVICE_ROLE_KEY`. Set these alongside any `CLOUD_*` aliases, pointing to the same existing backend. Generic aliases alone do not configure the generated clients. Never set conflicting values. Mark `SUPER_ADMIN_EMAIL` and all credentials/keys as private server-side values; only the two `VITE_SUPABASE_*` values are browser-visible.

**Backend key requirement:** because this deployment uses your own Supabase project, obtain its server-side service-role/secret key from that project’s API settings and add it to Cloudflare as `SUPABASE_SERVICE_ROLE_KEY` (and `CLOUD_SERVICE_KEY` if using the generic alias). Keep it private and never use a `VITE_` prefix. If you are still using a managed backend that does not expose a service-role key, privileged server features cannot be assumed to work on Cloudflare; use a backend you control or obtain the required server credentials from its provider.

### M-Pesa and SMS credentials

Enter Daraja and SMS provider credentials through the ShuleCloud Super Admin **Integrations** screen. The application encrypts these values using `INTEGRATIONS_ENCRYPTION_KEY` before storing them. Do not add Daraja consumer secrets, passkeys, or SMS API tokens to `VITE_*` variables or source files.

## Local Pages preview

1. Install dependencies with the package manager used by the repository.
2. Build with `npm run build:cloudflare`.
3. Create an ignored `.dev.vars` file in the project root containing only local test values for the server-side variables/secrets above. Do not use production credentials for local testing.
4. Preview the Pages output with `npx wrangler pages dev dist`.

The repository `.gitignore` already excludes `.dev.vars`, `.env`, and `.env.*` (while allowing `.env.example`). Never include `.dev.vars`, `.env.local`, or real credentials in a ZIP or commit.

## Release checks and limitations

Run `npm run preflight`, `npm run secret-audit`, `npm run security-audit`, `npm run typecheck`, `npm test`, and `npm run build` before production deployment. Then preview the Pages output and test authentication, all five roles, server routes, M-Pesa callback flow, scheduled endpoint, Google Drive OAuth, invitation email and backup flows using test credentials.

A passing static audit is not proof of a successful build, live Supabase security, live provider integration, or a production deployment. The ZIP author cannot configure your Cloudflare account or enter your private credentials; those steps must be completed in your Cloudflare dashboard.


## Moving away from Cloudflare later

1. Keep the same Git repository and Supabase project.
2. Choose a Nitro preset supported by the destination host, or deploy the standard Node output with `npm run build:node` on a compatible Node server.
3. Configure the destination host's environment variables and secrets using the same server-side names documented above. Never copy private keys into browser variables.
4. Update OAuth redirect URLs, webhook/callback URLs, scheduled-job configuration, allowed origins and the custom domain as required by the new host.
5. Deploy to a staging URL and verify sign-in, all five roles, server endpoints, M-Pesa callbacks, SMS, email, backups and scheduled tasks before changing production DNS.
6. Keep the existing Cloudflare deployment available until the new host is verified.

Changing hosting does not migrate Supabase data. Changing the backend/database provider is a separate migration and is not accomplished by changing `NITRO_PRESET` or `CLOUD_PROVIDER` alone.
